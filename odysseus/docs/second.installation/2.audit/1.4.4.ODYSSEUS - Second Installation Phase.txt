Phase 1.4 — Stage 1.3 review: Recovery scripts
The output is useful. We now have the complete contents of the four recovered operational scripts, their hashes, the legacy desktop launcher, and the Odysseus-related portions of CheckBox.

Conclusion: the recovery scripts contain some sound operational ideas, but none should be adopted as the new installation's implementation without redesign and retesting. They are historical evidence, not a trusted deployment.

odysseus_start.sh
Good design ideas:
- Checks for an existing process before launching another.
- Checks the recorded PID against the process command line.
- Starts only the specifically named ChromaDB container.
- Records whether it started ChromaDB, so a later stop can distinguish owned from pre-existing services.
- Uses a bounded health-check period.
Important problems:
- It launches Uvicorn on 0.0.0.0:7011, exposing the application on every available interface. That is not an acceptable default for an unverified application.
- distrobox-host-exec podman gives the application environment a route to host Podman control. This is a significant authority boundary, not merely a convenience.
- Its PID-file and process checks are useful operational safeguards, but they are not a security boundary.
- The script assumes the old project directory, Python virtual environment, and ChromaDB container exist. They do not currently exist in the inspected environment.
odysseus_stop.sh
Good design ideas:
- Sends TERM, not an immediate force-kill.
- Refuses to stop ChromaDB while an Odysseus process is detected.
- Stops ChromaDB only when its ownership marker exists.
- Retains the marker when shutdown cannot be verified.
Limitations:
- The ownership marker is a local file, not an independently verified ownership record. It can become stale or be inconsistent with the container's actual history.
- The process identity check relies on matching command-line text and a PID. It does not establish a robust process identity across restarts.
- It depends on the same host-Podman access described above.
odysseus_status.sh and odysseus_logs.sh
These are useful examples of separating status and log inspection from lifecycle operations.

One caution: the log viewer prints raw application logs. Logs can contain sensitive information, including credentials or request data. We should not automatically display or export them without reviewing the logging policy.
Legacy desktop launcher
This is the clearest rejection.

It uses:
pkill -9 -f "uvicorn app:app"
pkill -9 -f "chromadb.cli.cli"
pkill -9 -f "chroma run"


Those are broad pattern-based, forceful process kills. They are not restricted to an Odysseus-owned process. They could terminate unrelated applications.

It also references an old ai-box container, an old project path, and an old port arrangement. Do not run or reuse this launcher.
2. CheckBox integration
The inspected sections show a more careful approach than the desktop launcher:
- It checks the Odysseus container state.
- It checks the expected process arguments against the PID file.
- It distinguishes absent, verified, and unknown states.
- It tries to verify ChromaDB ownership before shutdown.
- It intends to keep the container running when shutdown cannot be verified.
That is a valuable operational pattern. However, CheckBox can invoke Odysseus's stop script and stop its Distrobox. It therefore needs a complete review before we can trust it as a shutdown authority.
