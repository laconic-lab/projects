## Confirmed MCP disabled-tool gap

The source now lets us make a stronger finding:

1. `routes/mcp_routes.py` persists per-server disabled tool names in `McpServer.disabled_tools`.
2. `agent_loop.py` loads those names into `_mcp_disabled_map`.
3. `_build_system_prompt()` passes that map to `get_all_openai_schemas()`, which omits the disabled tools from the model-facing schema list.
4. But `execute_tool_block()` does not receive that per-server map. Its runtime denylist is `disabled_tools`.
5. `McpManager.call_tool()` parses the qualified name and calls the MCP server without checking the server’s disabled-tool list.

So the per-server toggle is presently a visibility filter, not a proven execution barrier. This is a real policy-enforcement defect in the current source, not merely a theoretical concern. The separate global tool toggle is different: its names are added to the execution denylist, including qualified aliases for built-in email tools.

This is now a high-priority Agent audit finding. I am not changing anything; the next useful check is to reconcile the complete native registry and identify which tools bypass the registry through explicit dispatcher branches.
