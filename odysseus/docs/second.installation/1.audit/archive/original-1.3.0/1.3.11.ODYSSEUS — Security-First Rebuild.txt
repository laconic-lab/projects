## 2. What the scripts tell us about ChromaDB

The scripts confirm that the architecture was already split into two runtime layers:

`odysseus-box` — Distrobox

Odysseus application · Python 3.12.3 · project `.venv`

Application health: port 7011

Local HTTP communication

`odysseus-chromadb` — separate Podman container

Vector database service

Health endpoint: 127.0.0.1:8100

The START and STOP scripts manage the ChromaDB container through `distrobox-host-exec podman`. They record whether Odysseus started ChromaDB and only stop it when the ownership marker confirms that relationship.

That ownership behaviour is worth preserving. The scripts avoid starting duplicate application processes and avoid stopping ChromaDB if Odysseus did not start it. Those are useful operational safeguards.

However, these scripts do not prove that ChromaDB is securely isolated. We still need to inspect its actual container configuration, especially its mounts, port publishing, network mode, user mapping and persistence paths.

## 3. The important architecture distinction

We should not confuse two separate decisions:

- Where ChromaDB runs: a dedicated rootless Podman container.
- Where Odysseus and its Python `.venv` run: currently the documented `odysseus-box` environment.

Moving ChromaDB to Podman does not require moving Python into a different container. Conversely, moving the application into a hardened container introduces a separate Python environment migration question.

My recommendation is to preserve the existing `.venv` as the reference baseline while we design the secure runtime. We should not recreate it just to satisfy a container architecture decision.

If the final security boundary requires the application itself to move into a dedicated Podman container, we must first decide how to preserve its interpreter and dependencies reproducibly. A virtual environment generally contains interpreter paths and assumptions about its original environment; it should not simply be copied into an arbitrary new container and presumed portable.

## 4. A correction to the network proposal

The current scripts use `127.0.0.1:8100` for ChromaDB health checks. That establishes the address the script expects to reach, but it does not establish how the container publishes that port or whether the endpoint is accessible from other interfaces.

Before deciding whether Odysseus should have no direct network access, we need to establish how the application communicates with ChromaDB and which other network capabilities the application actually requires.

A no-network application container could still be feasible, but only if its required services are accessible through explicitly approved IPC or another carefully constrained mechanism. We must not break ChromaDB or the application merely to achieve a theoretical boundary.
