I've retrieved and examined all five tests from your GitHub document.

Initial verdict: the Steam Deck is technically well equipped to host the proposed rootless Podman runtime. The essential building blocks are already present: rootless Podman, subordinate UID/GID ranges, cgroup v2, seccomp, crun, and the pasta network backend.

However, there are two important areas that still need engineering work before we can approve the runtime design:
1. Identity and credential isolation: rootless Podman currently maps container UID 0 to host UID 1000 (deck). We must design around that fact, not assume that container root is a separate host identity.
2. Network isolation: the existing pasta networking does not by itself establish our required outbound allowlist or prove that host and LAN access are blocked.
Neither issue means we need to abandon Podman. They mean we must be precise about the configuration and test it before trusting it.

2. Identity mapping — the important detail
Your host has:
deck UID = 1000
deck GID = 1000

/etc/subuid:
deck:100000:65536

/etc/subgid:
deck:100000:65536


Podman's current mapping is:
Container ID	Host ID	Size
0	1000	1
1	100000	65536

This means:
- Container root maps to host deck.
- Container UID 1 maps to host UID 100000.
- The remaining subordinate range is available for additional mappings.
This is normal rootless Podman behaviour, but it is a crucial security consideration.

Our correction to the initial design: we cannot simply promise that the container will have no relationship to host UID 1000. Rootless operation depends on a host user owning the container process. What we can do is prevent that mapped identity from obtaining broad host access through filesystem mounts, sockets and host interfaces.

I recommend evaluating a separate auto or nomap mapping for the application, with a dedicated unprivileged container user. We must verify actual mappings and bind-mount permissions before selecting one.
3. Kernel isolation and resource controls
Good foundation
Your SteamOS installation reports:

- Podman seccomp enabled, using /usr/share/containers/seccomp.json.

This is a strong foundation for resource and process isolation.

One distinction matters: the host shell reports Seccomp: 0, but that does not mean Podman containers run without seccomp. The Podman runtime reports seccomp enabled. We have not yet launched a test container to verify the effective restrictions inside it.

There is also no active AppArmor or SELinux framework reported. That removes two potential additional layers of defence. It is not an automatic blocker, but we must not claim that this configuration has mandatory access-control protection.

Assessment: suitable for continuing the design, with effective container restrictions still to be tested.

Podman documents both its capability-dropping controls and cgroup resource limits. It also notes that some rootless systems can reject resource-limit changes, so controller availability alone is not proof of successful enforcement.

4. Networking — the largest unresolved security issue
Requires architectural refinement
Your results show:
- Ethernet interface: 192.168.1.161/24.
- Active IPv6 global addresses and default route.
- firewalld running in the public zone.
- nftables available.
- Rootless networking through pasta.
- Netavark as the Podman network backend.
The important detail is that rootless Podman uses pasta by default. Its normal networking configuration can copy the host's IPv4 and IPv6 addresses and routes into the container's network environment. The default configuration also avoids direct gateway access, but that does not establish a complete LAN or internet egress policy. 

Podman documentation+1

We must therefore treat the following as unverified:
- Whether the container can reach other LAN devices.
- Whether IPv6 provides a route around IPv4 restrictions.
- Whether host services are reachable through any mapped address.
- Whether direct internet traffic can bypass an approved proxy.
My recommended refinement
I would now prefer a stricter model than the original general egress-gateway design:
ODYSSEUS CONTAINER
No direct network
Private network namespace, no network interface or direct outbound connectivity

One explicitly approved IPC interface

HOST-SIDE BROKER

Provider requests · approved research requests · project inspection


Approved cloud APIs


Approved research




Podman supports --network=none, which creates a network namespace without configuring network interfaces or connectivity. 

Podman documentation

This would give us a much smaller attack surface:
- The Agent cannot directly browse the internet.
- It cannot directly connect to the LAN.
- It cannot use IPv6 as an alternate route.
- It cannot bypass the broker with a different HTTP client.
- The host-side broker performs only registered operations.
The remaining challenge is secure communication through a narrowly mounted Unix socket or equivalent IPC channel. We must verify its permissions and authentication with the selected user namespace.

I recommend this as the preferred network design, subject to your approval.

What I propose next
Once these results are examined, I can deliver the final SteamOS-specific feasibility report and a revised implementation blueprint.

The key design decision I want to preserve is this:

Odysseus should have no direct network access. Its approved host-side broker should be its only doorway to external services and approved project information.

That is a cleaner security boundary than attempting to make a general-purpose container network safe through a collection of firewall exceptions.

No implementation has begun, and the existing projects remain outside the scope of this examination.
