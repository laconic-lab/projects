First important security finding
The upstream threat model itself explicitly says Odysseus has no shell or filesystem sandbox. Its bash, read_file and write_file tools run as the application process user, without filesystem confinement or network-egress filtering.

The new tool-approval gate is described as a compensating control, not a sandbox. The threat model also acknowledges that request-level authority can be broader than the user's exact requested action: for example, a request to read email may admit both send_email and delete_email. That is a significant distinction for our least-privilege design.

Source: Canonical threat model.
Step 2 — The security gate is real, but it is not the whole boundary
The code contains a deterministic capability registry. It classifies tools by effects—reading private data, writing, executing code, network egress, external side effects, administration and destructive actions. Unknown tools are deliberately classified as high-impact and untrusted.

After untrusted content is introduced, the run-security context blocks high-impact effects unless an approval path is satisfied. Importantly, the implementation also distinguishes a real server-issued approval from a client merely editing chat metadata: chat-session approvals are HMAC-signed and bound to the session and approval ID.

That is meaningful security engineering. But it does not make every approval equally narrow: task and chat-session approval scopes can extend beyond a single action. We need to understand exactly how the approval card seals the first action, what later calls a session grant permits, and how current policy is rechecked.

Sources: tool capability registry, approval-scope implementation.
Correction after checking the implementation, not just the threat-model prose
I found an important documentation/code mismatch, so I am correcting the earlier broad statement.

The current implementation has evolved beyond the older threat-model description:
- Native agent filesystem tools have canonical path confinement, workspace/resource binding, and sensitive-path checks.
- Native model-controlled Bash/Python execution uses an enforcing containment layer. Its required dimensions are filesystem scope, process-tree control and wall-clock limits. If those required controls cannot be established, execution is refused.
- Network isolation is not part of that required baseline: the containment documentation says networking is inherited unless explicitly requested. Memory and process-count limits are also not universally guaranteed.
- The TUI host-shell bridge is a separate execution route. Its containment grant describes an external execution environment; Odysseus cannot enforce that grant locally.
So the accurate conclusion is not “there is no containment”. It is: native execution has real, fail-closed containment, but it is not a complete network-isolated sandbox, and external host execution has a different trust boundary.

The older THREAT_MODEL.md is therefore stale on this point. The newer implementation map in specs/auth-security.md and src/containment.py is more accurate for the current commit.
Step 3 — Runtime and deployment risks
The source audit has exposed several defaults that conflict with our intended manual-start, local-only, low-autonomy deployment.
Upstream default	Why it matters to Odysseus
Compose restart: unless-stopped	Containers can return after a host or Docker restart. Conflicts with manual lifecycle.
In-process task scheduler enabled	Scheduled tasks can run unless explicitly disabled.
Built-in MCP registration at startup	Several MCP subprocesses are started automatically.
Browser MCP uses npx -y @playwright/mcp@latest	The first startup can fetch and run a floating npm package version.
Host gateway added to the app container	The container can reach host-side services; this is not an isolated network boundary.

There is a subtle but important MCP detail: ODYSSEUS_DISABLE_MCP=1 disables the built-in MCP registrations, but startup separately calls connect_all_enabled() for user-configured MCP servers. So that flag alone is not a universal MCP kill switch. A fresh database with no enabled user servers, plus disabled MCP administration and verified dispatch restrictions, is the safer initial posture.

The positive findings are equally important: the default Compose file does not mount the Docker socket, and it does not mount the host's entire home directory. Its normal mounts are application data, logs, and app-specific SSH/cache/local directories. We should preserve that narrow boundary.

Source files: Compose, built-in MCP registration, application startup.
Step 4 — The ordinary-user boundary
The role split in the source is clear:
- Admin: full privileges. The admin is not a safe everyday Agent identity.
- Non-admin: shell, Python, host shell, native file tools, email, MCP, memory-management tools, settings, integrations and other privileged tools are blocked server-side.
- The non-admin defaults still permit several features, including Agent, browser, research, documents and image generation. can_manage_memory also defaults to true, although the direct manage_memory tool is separately blocked for non-admin users. We should explicitly tighten that privilege rather than rely on the tool block alone.
One requirement needs a deliberate architecture solution: the built-in non-admin cannot inspect project files, because read_file, grep, glob, ls and get_workspace are all in the non-admin blocklist.

I will not work around that by granting general filesystem access. The right design is a dedicated, read-only project-inspection capability with a fixed approved root, bounded output, no path escape, no writes, and no shell. We must verify its server-side enforcement before exposing it to the ordinary Agent.

The encouraging part: upstream now enforces the global disabled-tool denylist again at execution time, not merely when building the model's tool list. Its manage_settings chat tool can disable tools, but cannot re-enable tools that an admin disabled; re-enabling is reserved for the human Settings interface.

Sources: non-admin tool policy, tool execution enforcement, admin tool controls.

Step 8 — Remaining blockers before a safe deployment
Must resolve before installation
1. Distrobox host-home exposure

This is particularly important on the Steam Deck. The normal Distrobox arrangement exposes the host home directory read/write. The container process also runs with the host user's UID.

That means a host key protected by mode 600 is still readable by an Odysseus process running as the same user if the key's directory is mounted into the container.

Our rule must be stronger than file permissions:
- No /home/deck mount.
- No broad host filesystem mount.
- No host .config mount.
- No privileged container or host networking.
- Verify the actual UID/GID, mounts and security profile.
We must prove the odysseus-box runtime meets those conditions before starting the application. Distrobox isolation cannot simply be assumed.

2. Provider credential architecture

Upstream stores model endpoint API keys encrypted in its database. That protects stored data at rest, but the running application can decrypt those keys.

That is not the architecture we established.

The Groq key must remain host-side:

/home/deck/.config/odysseus/providers/groq/odysseus-groq.key

The app must use a narrow provider-broker interface. It must never receive the raw key, and we must not put it in DbSession.headers, session metadata, logs, browser state or source files.

Groq remains the first provider. The other six remain future integrations. Manual selection only; no automatic switching, fallback or paid API usage without explicit authorization.

3. Approval scope

The approval implementation cryptographically seals the exact first action. However, the chat approval choices can grant continuation for the resumed task or the whole chat session.

That is broader than approving one operation and nothing else. We will keep high-impact capabilities disabled initially. Before enabling them later, we must decide whether to modify the approval flow to provide a strict single-action choice.

4. Read-only project inspection

The normal non-admin Agent cannot use upstream's filesystem tools. We need a separate, fixed-root project-inspection interface.

It must have:
- A fixed approved project root.
- Read-only access.
- No arbitrary paths or path traversal.
- Bounded file sizes and output.
- No shell, Python, writes or deletes.
- Explicit server-side capability classification and tests.
I prefer a narrow host-side inspection interface over exposing the host filesystem to the application container.
