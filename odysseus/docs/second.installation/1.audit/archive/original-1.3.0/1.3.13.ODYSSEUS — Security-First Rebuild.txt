### 1. The decisive security finding

This is the most important discovery in the archives.

The old `odysseus-box` inspection reported:

Unsafe isolation for our threat model

| Setting           | Previous configuration |
| ----------------- | ---------------------- |
| Privileged        | `true`                 |
| Container user    | `root:root`            |
| Network           | `host`                 |
| AppArmor          | `unconfined`           |
| Capabilities      | Not explicitly dropped |
| Host home         | Mounted read/write     |
| `/run/host`       | Mounted read/write     |
| `/run/user/1000`  | Mounted read/write     |
| `/dev` and `/sys` | Exposed read/write     |

This explains why the Groq key was readable from inside Odysseus, even though the key was stored outside the project directory.

It also establishes why simply adding agent instructions, tool blacklists or an application-level permission list is insufficient.

The agent must not be trusted to enforce its own security boundaries. The operating system and container boundary must enforce them independently.

One important clarification: Groq itself does not gain remote shell access to your Steam Deck simply because Odysseus uses a Groq API key. The risk was that the local Odysseus process, including its potentially powerful agent tools, could access host resources and potentially disclose information.

## My recommended architecture for the new implementation

## ODYSSEUS — Proposed security architecture

STEAM DECK HOST — Trusted boundary

Host-owned resources and controlled interfaces

Provider credentials

Host-only key files, inaccessible to the agent container

Read-only inspector

Fixed paths, bounded operations, no shell

Explicitly controlled interfaces

## Rootless Podman — Odysseus application

Dedicated isolated runtime · non-privileged · restricted capabilities

Odysseus Agent + UI

Independent agent permissions, no unrestricted host access

Private application network

ChromaDB reachable only through the intended application connection

Manual lifecycle, restricted UI exposure

Windows PC — 192.168.1.169

Authorized browser access to Odysseus UI

This is the architecture I recommend investigating and implementing.

A few design decisions are especially important:

- Rootless Podman: the application must not run as a privileged container.
- ChromaDB: ideally place it on a dedicated private container network, without exposing its port to the LAN.
- Provider broker: the agent requests a permitted provider operation; it never receives the host credential itself.
- Inspector: a separate, restricted interface for reading specifically approved project files and bounded logs.
- Agent tools: server-side authorization, not merely hidden tools or instructions.
- Manual lifecycle: no boot autostart, automatic restart, background scheduling or provider fallback.
- UI: expose port 7011 only to the authorized Windows PC.

One nuance: the broker and inspector must themselves be designed carefully. A mounted socket is not automatically secure. We must authenticate the caller and constrain every operation.
