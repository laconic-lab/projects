## First new finding from the current upstream audit

The current `dev` branch of `odysseus-dev/odysseus-current` is not a lightweight chat application. Its published Compose configuration starts a multi-service workspace.

It includes:

- Odysseus application
- ChromaDB
- SearXNG
- ntfy

More importantly, its default configuration includes persistent application data, logs, SSH identity storage, local model caches and installed Python tooling. It also configures internal service discovery and host-service access.

This is a significant architectural consideration: we should not assume that putting the standard upstream Compose stack inside rootless Podman automatically gives us the isolation we want. We need to audit every service, mount, environment variable, startup action and network path before adapting it.

## Findings that change our implementation plan

Must be addressed before deployment

| Finding                 | Evidence in upstream                                                                                     | Our decision                                               |
| ----------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Automatic restart       | All four Compose services use `restart: unless-stopped`                                                  | Replace with manual lifecycle                              |
| Host connectivity       | `host-gateway` is explicitly configured                                                                  | Remove unless a specific, justified connection is approved |
| Persistent SSH identity | `data/ssh` is mounted into the application                                                               | Do not expose host SSH credentials or identities           |
| API credentials         | Numerous provider and search keys are passed through environment variables                               | Use our controlled provider broker                         |
| Background activity     | In-process pollers and tasks default to enabled                                                          | Disable and inspect every background mechanism             |
| MCP startup             | Built-in Python MCP servers and an NPX browser server are registered automatically                       | Disable by default and audit server-side execution         |
| Application privileges  | Main application has no explicit capability-drop or read-only filesystem policy in the base Compose file | Design explicit restrictions                               |
| ChromaDB version        | Compose uses `latest`                                                                                    | Pin a verified version and digest                          |

### 1. The Python version has changed

The historical installation used Python 3.12.3.

The current Dockerfile builds on Python 3.14. This is not a trivial difference: it affects dependency compatibility, compiled wheels and the existing virtual environment.

We must not reuse the old `.venv` blindly, nor assume that the old dependency list is still appropriate.

My recommendation is to treat the upstream Dockerfile as a dependency reference, then establish a reproducible Python environment for the final deployment.

### 2. MCP deserves its own audit

The current `src/builtin_mcp.py` automatically registers:

- Image generation
- Memory
- RAG
- Email
- Browser automation through Playwright MCP

The browser server can use `npx -y` and install its package during startup. The source explicitly provides an environment setting to require a pre-existing cache instead.

There is another important detail: disabling built-in MCP registration does not, by itself, prove that all MCP execution paths are disabled. The tool dispatcher has native fallback implementations.

We need to inspect both the advertised tools and their actual execution paths.

Relevant source: [builtin_mcp.py](https://github.com/odysseus-dev/odysseus-current/blob/dev/src/builtin_mcp.py?utm_source=chatgpt.com)

### 3. Upstream itself acknowledges a security limitation

The current `THREAT_MODEL.md` explicitly acknowledges:

- No shell/filesystem sandbox.
- Shell and file tools execute with the application process user's permissions.
- Prompt injection can potentially reach these tools.
- There are known SSRF concerns.
- Token scopes are coarse.

This is an important distinction.

Odysseus has application-level security controls, but its own documentation does not claim that those controls provide operating-system isolation.

Our independent container boundary is therefore justified.

### 4. The most important architectural correction

I would no longer recommend deploying the entire upstream Compose stack unchanged.

Instead, I recommend a minimal, purpose-built deployment derived from upstream, retaining only the components we actually need.

| Component             | Initial decision                                                |
| --------------------- | --------------------------------------------------------------- |
| Odysseus              | Required                                                        |
| ChromaDB              | Required if confirmed by the selected application configuration |
| SearXNG               | Optional; decide after inspecting search requirements           |
| ntfy                  | Excluded initially                                              |
| Host Docker socket    | Prohibited                                                      |
| Host SSH identity     | Prohibited                                                      |
| Host home directory   | No broad mount                                                  |
| Provider credentials  | Host-side broker only                                           |
| Automatic browser MCP | Disabled                                                        |
| Background scheduler  | Disabled initially                                              |

This reduces the number of moving parts and the number of possible security paths.

## What I want to examine next

I suggest the next audit be focused on three areas, in this order:

A. Agent authority

- Tool registration and tool schemas.
- `execute_tool_block()` and native fallbacks.
- Admin and single-user authorization.
- MCP dispatch and external MCP configuration.
- Bash, Python, filesystem and background execution.
- Scheduler, pollers and automatic reconnection.

B. Container isolation

- Rootless UID/GID mapping.
- Writable bind mounts and ownership.
- ChromaDB networking.
- DNS and outbound connectivity.
- Host service reachability.
- CPU, RAM, PID and storage restrictions.

C. Credential protection

- Provider key access.
- Environment variable exposure.
- Process inspection and logs.
- Broker authentication.
- Protection against reading unrelated host credentials.

The local Steam Deck tests must remain non-destructive. We should inspect the current state before issuing commands that might accidentally start or stop anything.
