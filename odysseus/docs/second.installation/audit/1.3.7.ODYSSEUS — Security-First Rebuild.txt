ODYSSEUS — Phase 2.2: Container and host-boundary examination
We’ll now examine whether odysseus-box can keep Odysseus contained without exposing the Steam Deck host, its credentials, or unrelated projects.

The central question is not whether Distrobox is convenient or whether the container has its own name. It is:

Can a compromised Odysseus process read or modify something on the Steam Deck simply because it runs inside odysseus-box?

We’ll assess the boundary in four areas: filesystem and identity, process and privilege exposure, network and service access, and the two narrowly controlled host interfaces (provider broker and project inspector).

This remains a design examination. No Deck commands, container changes, key access, installations or provider calls.
1. The fundamental Distrobox limitation
Not a security sandbox by default
The official Distrobox documentation is unusually explicit: Distrobox is designed for tight host integration, not strong isolation. Its normal setup can share the user's home directory, external storage, devices, network, process visibility and desktop/session interfaces. The project itself warns users not to treat a standard Distrobox as a highly isolated sandbox. 

GitHub+1

That directly affects our design.

A normal odysseus-box cannot be assumed to protect the Steam Deck host from a compromised process running as deck.

This is particularly important for the provider keys. A host key file with mode 600 is protected from other Unix users, but not from another process running under the same host UID if that file is visible inside the container.

A custom container home directory does not solve this by itself: Distrobox documentation says that choosing a custom home does not necessarily prevent the host home from being mounted. 

Debian Manpages+1

2. The current odysseus-box is already known to cross the boundary
We have more than a theoretical concern here. The previous inspection of your actual container established:

The container's runtime configuration also showed root:root, while its interactive session and Python process run as UID/GID 1000. The effective process identity and mounted paths matter more than the container's displayed name or default runtime configuration.

Most importantly, the earlier inspection confirmed that the container can read the existing Groq key at:

/home/deck/.config/odysseus/providers/groq/odysseus-groq.key

That file is mode 600, but the same-UID process can read it because the host home is mounted into its environment. The permissions are behaving as designed; the mount and identity arrangement defeats the intended separation. 

This is a confirmed isolation failure for our requirements—not a hypothetical risk.
3. Exposure assessment by resource
Here is what the current configuration means in practice.

A few details deserve emphasis.
A. Host filesystem
The /home/deck mount is the largest problem.

It exposes much more than the Odysseus project:
- /home/deck/.config
- /home/deck/.ssh
- /home/deck/OdysseusProject
- /home/deck/OdysseusRecovery
- Other project directories
- Provider credentials
- User-owned application data
This violates our separation requirements, including the protection of your LocalAI, Pi-hole and Stable Diffusion projects.

The /run/host mount creates an additional route to the host filesystem. Removing only the /home/deck mount would not be enough while that alternative route remains accessible.
B. User-session interfaces
The /run/user/1000 mount is particularly interesting.

On Linux, this directory can contain session sockets for services such as:
- D-Bus
- PipeWire
- Desktop portals
- User-level services
- Rootless Podman, if its API socket is active
We have not established that every one of these sockets is currently available inside odysseus-box. But exposing the entire directory unnecessarily increases the attack surface.

Our design should not expose the host user-session runtime directory.
C. Network and processes
Distrobox normally shares the host network and process namespaces. Its documentation provides unsharing options, but explicitly warns that these do not turn it into a complete security sandbox. 

ArchWiki+1

This matters because Odysseus will communicate with cloud providers, research services and potentially local services.

We want outbound access for approved operations, not unrestricted access to the Steam Deck's local network.

4. Would Distrobox isolation flags solve this?
Unfortunately, not completely.
Distrobox feature	What it changes	Does it solve our problem?
'--unshare-netns	Separates network namespace	No, home remains exposed
'--unshare-process	Separates process namespace	No, home remains exposed
'--unshare-devsysfs	Separates devices and sysfs	No, filesystem remains exposed
'--unshare-all	Enables the available unsharing options	No, mandatory home/application integration remains
Custom --home	Changes the container's home directory	No, it does not necessarily prevent the host home mount

The important distinction is that Distrobox's design requires certain host integrations. Its documentation explicitly identifies home and application access as integrations that cannot be unshared in its normal model. 

ArchWiki+1

So I would not spend time trying to turn the existing odysseus-box into a security boundary by adding more Distrobox flags.

It is the wrong abstraction for this particular requirement.

5. Recommended architecture: dedicated rootless Podman
Recommended direction
I recommend retaining the Ubuntu 24.04 environment concept, but changing how Odysseus is isolated.

Instead of using Distrobox as the execution boundary, use a dedicated rootless Podman container with explicitly controlled mounts and namespaces.

This is feasible to investigate because Podman 6.0.2 is already available on your Steam Deck host.

6. Provider broker — how to protect the Groq key
We should change the previous direct key-file resolver approach.

The host must retain ownership of the credentials:

/home/deck/.config/odysseus/providers/groq/odysseus-groq.key

Odysseus must not mount that directory.

Instead:
Odysseus container

Requests an operation using the selected provider


Host provider broker
Credential boundary
Validates provider, model, request size and permitted operation


Host-held provider key

Read internally; never returned to the container


Approved provider API

Broker constructs the authenticated request and returns the response


The broker must:
- Accept only registered provider IDs.
- Accept only approved provider endpoints.
- Construct authentication headers internally.
- Reject arbitrary URLs and caller-supplied authentication headers.
- Never return raw credentials.
- Never log secrets or authentication headers.
- Keep provider selection explicit.
- Never switch providers automatically.
- Enforce request limits and reject unauthorized operations.
A mounted Unix socket could be considered as the communication mechanism, but the socket's existence alone is not authorization. The broker must validate every request.
7. Read-only project inspector
The project inspector needs a similarly narrow design.

The Agent should not receive a general mount of /home/deck/OdysseusProject.

Instead, the host-side inspector should expose only specifically approved operations:
Operation	Permission
List approved project files	Read
Read approved configuration	Read
Read bounded logs	Read
Inspect project health	Read
Read recovery manifests	Read, where approved
Write or edit files	Deny
Delete files	Deny
Read arbitrary host paths	Deny
Execute shell commands	Deny
Follow paths outside approved root	Deny

The inspector must also reject symlink escapes, special files, oversized reads and arbitrary path traversal.

That gives Jarvis the ability to understand Odysseus without handing it the host filesystem.

8. Upstream Docker deployment: another reason not to copy it unchanged
I also checked the pinned upstream deployment files.

The supplied Compose configuration is designed for a fuller Docker deployment, not our restricted Steam Deck arrangement.

A few examples:
- It provides host.docker.internal access to host services.
- It defaults to automatic container restart.
- Its task and email-poller background switches default to enabled.
- The Dockerfile installs network diagnostic utilities, SSH client, tmux, Chromium, Node/npm and a Docker CLI.
- The Dockerfile documents an optional Docker socket integration for Cookbook functionality.
The default Compose file does not itself mount the Docker socket, but the optional integration is not appropriate for our deployment.

We should not simply transplant upstream Compose into the Deck environment. We need a deliberately smaller runtime profile.

9. Final assessment
Current odysseus-box
Rejected as security boundary

It exposes too much of the host filesystem, host identity and session environment.
Distrobox with unsharing flags
Insufficient

Useful for partial separation, but mandatory host integrations remain.
Dedicated rootless Podman
Recommended

Allows us to design explicit mounts, namespaces, user mappings and a smaller attack surface.
Dedicated virtual machine
Stronger alternative

Provides a stronger isolation boundary, but brings additional resource and operational overhead.
My recommendation
I would choose dedicated rootless Podman, with a private network namespace, explicit filesystem mounts and the two narrow host interfaces.

We should retain the existing odysseus-box for now. There is no reason to delete it or change its configuration during this examination.

The next step should be a detailed Phase 2.2 architecture specification, covering:
1. Container identity and UID/GID mapping.
2. Exact filesystem mount allowlist.
3. Network and egress policy.
4. Provider broker protocol.
5. Project inspector protocol.
6. Container lifecycle and resource limits.
7. Security acceptance tests.
Only after that specification is agreed should we prepare implementation steps.

One important distinction: the current Groq key exposure is confirmed, but no key contents have been accessed during this examination. The key should remain where it is; our next design must remove the container's route to it, not move the key into another application or mount.
