Agent audit — second pass: execution routes and automatic activity
This pass confirms that the Agent is not the only execution route. There are several independent ways for Odysseus to initiate work.
1. Interactive chat authority
Owner propagation verified
The chat route obtains the current user, resolves the effective owner, and passes that owner into stream_agent_loop().

That is good: the Agent does not simply receive an arbitrary owner supplied by the model. However, API-token requests have a separate identity model:
- Bearer tokens are represented internally by the pseudo-user api.
- effective_user() resolves the actual token owner when available.
- Token permissions and scopes are checked separately by the authentication layer.
This needs dedicated testing because the same owner value is not necessarily equivalent to the same permissions. In particular, an API token must not inherit the full authority of the account that created it.

Sources: auth_helpers.py, chat_routes.py.
2. Startup automatically activates background mechanisms
Important deployment conflict
The application startup sequence explicitly starts several mechanisms:
Mechanism	Startup behaviour	Implication
Background-job monitor	Started automatically	Can resume Agent work
Built-in MCP registration	Started automatically	Registers built-in tool servers
Configured MCP connections	Connects enabled servers	External integrations may become active
Task scheduler	Enabled by default	Scheduled tasks can execute
Default task reconciliation	Runs during startup	Creates or updates default automation tasks
Other housekeeping loops	Started automatically	Background activity continues independently

The scheduler can be disabled with ODYSSEUS_INPROCESS_TASKS=0, but that does not disable the background-job monitor or MCP startup.

The background-job monitor is particularly important: it polls every five seconds and can invoke stream_agent_loop() again with the completed job's output. That follow-up is not merely a notification. It can execute additional tools.

Sources: app.py, bg_monitor.py, task_scheduler.py.
3. Scheduled tasks have their own execution authority
Separate execution surface
The scheduler supports more than model-driven tasks. Its built-in actions include:
- ssh_command
- run_script
- run_local
The implementations invoke Bash or another shell, and SSH can execute commands on another machine.

This is important because blocking interactive Agent Bash would not, by itself, prevent a scheduled action from executing a script.

The scheduler has an admin privilege check for admin-only actions, but we must still audit task creation, ownership, action classification, and every route that can dispatch these tasks.

Sources: builtin_actions.py, task_scheduler.py.
4. The internal application API is another capability bridge
app_api is a generic internal HTTP client for Odysseus routes.

It has:
- An endpoint-discovery mode using OpenAPI.
- A blocklist for sensitive routes and certain host-control operations.
- An internal authentication token.
- Owner propagation for internal requests.
That is useful architecture, but it creates a large review surface: every route reachable through the internal API needs its own authorization and side-effect review. A blocklist is only as complete as its knowledge of the routes.

Source: src/tools/system.py.
5. Host shell and MCP registration
Two additional findings:
- The user-facing shell routes are separately admin-gated. Their no-auth behaviour needs careful deployment review; an application with no configured authentication is not automatically safe simply because the shell route calls itself admin-only.
- The Agent-facing manage_mcp implementation has a command allowlist and denies common interpreters, shells, package runners and other dangerous launchers. That is a useful mitigation for one registration path, but it does not prove that the admin MCP configuration route or every other server registration path has the same restrictions.
Sources: shell_routes.py, admin_tools.py.
