ODYSSEUS — Phase 2.1: Dispatch and authority audit
Let's go. We’ll keep this phase strictly read-only: inspect how Odysseus actually authorizes and dispatches tool calls, identify bypasses, and turn the findings into a concrete security policy.

No Steam Deck commands, no installation, no configuration changes, no provider/API calls, and no credential access.

The key principle for this audit is:
A tool being hidden from the model is not the same as the server refusing to execute it.

We need to verify enforcement at the actual execution boundary—not just in the UI, prompt, or tool catalogue.
First findings: the security boundary is real—but it has several layers
The pinned dev revision has a substantial server-side authority mechanism. This is stronger than simply hiding dangerous tools from the model:
- Each tool operation is normalized into a canonical operation identity.
- The dispatcher checks a server-owned request authority bound to the owner, session and workspace.
- Tool permissions can be narrowed by policy and disabled-tool settings.
- A turn contract adds another restriction.
- Child/continuation authorities are intersected with parent authority rather than being allowed to expand it.
That is a good foundation. However, it does not yet mean the default Odysseus configuration matches our intended restricted Agent. We still need to account for single-user/admin identity, MCP, startup jobs and alternate execution surfaces.
1. Native tool dispatch
Strong enforcement foundation
At the pinned commit, execute_tool_block() performs these checks before reaching the tool handler:
1. Requires an explicit security context.
2. Applies delegated-credential restrictions.
3. Retrieves the active server-owned RequestAuthority.
4. Intersects a supplied child authority with its parent.
5. Normalizes the requested operation.
6. Verifies authority is bound to the expected owner, session and workspace.
7. Applies disabled-tool and policy restrictions.
8. Checks the turn contract.
9. Resolves backend, process, filesystem and other resource identities.
10. Applies external-content approval requirements where relevant.
11. Only then dispatches the operation.
A model-generated tool call therefore cannot create its own server authority simply by naming a tool or forging its arguments.

Important distinction: the dispatcher protects calls that pass through this execution path. We must still ensure no alternative route bypasses it.

Source: src/tool_execution.py · src/agent_runtime/authority.py
2. Admin and single-user authority
Odysseus design blocker
This is one of the most important findings for our deployment.

The upstream function owner_is_admin_or_single_user() deliberately returns True when authentication is disabled.

That is intentional for a conventional single-user self-hosted installation: the local operator is treated as having full access.

But our intended arrangement is different:
- We operate the application.
- The ordinary Odysseus Agent must have a restricted set of capabilities.
- The Agent must not inherit our administrative authority merely because it runs as the local owner.
The existing non-admin blocklist is not sufficient for that requirement. In single-user mode, it is bypassed by design.

Required design: introduce an independent Agent capability profile that applies even when the human operator is an administrator or authentication is disabled.

The two identities must remain separate:
Human operator — administrative authority

Can configure Odysseus, manage providers, and administer the application through explicitly authorized interfaces.


Ordinary Agent — restricted authority

Can chat, use the selected provider, perform controlled research, and inspect approved project information. No inherited administrator powers.


Source: src/tool_security.py · tests/test_review_regressions.py
3. MCP dispatch
Must be hardened for our deployment
The MCP manager and the execution dispatcher have deliberately separate responsibilities.

The manager can execute a qualified name such as:

mcp__server_id__tool_name

But McpManager.call_tool() does not itself own the user/admin/disabled-tool authorization policy. Its callers must enforce those checks.

The current architecture has several protections:
- MCP tools are hidden from schemas when disabled.
- Non-admin policy blocks the mcp__ namespace.
- Request authority can explicitly disable MCP.
- MCP calls are subject to the central dispatcher.
- Raw Playwright browser MCP calls are rejected where they cannot establish the required browser authority.
However, the upstream shell/MCP specification explicitly documents an important gap:

Per-server disabled MCP tools are hidden from prompts and schemas, but are not a complete execution-time denial if a disabled qualified name reaches the dispatcher.

This is exactly why our policy should not rely on hiding tools.

For Odysseus, the simplest safe rule is:
- No user-configured MCP servers.
- No built-in MCP servers.
- No dynamic MCP tool exposure.
- No qualified MCP calls, regardless of server or tool name.
- Server-side denial before McpManager.call_tool().
We should enforce this at the dispatcher and retain a second denial inside the MCP call boundary as defence in depth.

Sources: src/mcp_manager.py · specs/shell-mcp.md
4. Alternate execution routes
The audit confirms that the central Agent dispatcher is not the only execution surface.
Execution route	Upstream situation	Odysseus requirement
Native Bash / Python	Central dispatch and containment	Deny
Native filesystem tools	Central dispatch and path confinement	Deny general access
MCP	Separate manager and policy layers	Disable completely
Admin shell HTTP routes	Separate admin-only routes	Never expose to Agent
Host-shell TUI bridge	External execution environment	Do not connect
Background Bash jobs	Detached execution and monitoring	Deny
Scheduled tasks	Separate scheduler and authority paths	Disable
Browser automation	Native browser and MCP paths	Controlled read-only browser only
API integrations	Generic integration tools	Deny
Email and messaging	Native and MCP paths	Deny

The host-shell bridge deserves special attention
The TUI bridge is not simply another local tool handler. It transports execution into an external environment.

The Odysseus dispatcher can control which tools are routed through the bridge, but it cannot independently enforce the host's filesystem and process restrictions.

For our initial installation, I recommend not connecting this bridge at all.
Background execution is also broader than one scheduler
The startup code launches several independent background components, including:
- Background-job delivery and monitoring.
- MCP registration and configured-server connections.
- Tool-index warmup.
- Scheduled-task processing, enabled by default.
- A periodic owner-maintenance sweep.
- Cookbook process lifecycle monitoring.
- Process cleanup/reconciliation.
The email poller has a separate switch, ODYSSEUS_INPROCESS_POLLERS.

This means switching off the task scheduler alone does not disable all background activity.

We must define a deliberate startup profile, not assume that one environment variable creates a manual-only application.

Sources: app.py · routes/email/email_pollers.py · specs/shell-mcp.md
5. Regression coverage
The upstream project already contains meaningful security tests.

Examples include:
- Request authority and execution denial.
- Delegated API-token restrictions, including forged tool offers.
- External-context tool gating.
- Raw browser MCP execution restrictions.
- Disabled qualified/bare email alias handling.
- Native filesystem resource identity checks.
Useful starting points:
- tests/test_request_authority.py
- tests/test_api_token_tool_authority.py
- tests/test_external_context_tool_gate.py
- tests/test_browser_identity_transport.py
For our own restricted profile, I would add dedicated tests for:
1. An administrator-owned Agent still cannot invoke denied tools.
2. Authentication-disabled mode does not expand Agent permissions.
3. Forged MCP calls are rejected even when omitted from the model schema.
4. Disabled MCP servers cannot be called directly.
5. No unknown or newly introduced tool is executable by default.
6. A provider cannot expand the Agent's tool permissions through its returned tool calls.
7. A child/background task cannot acquire more authority than its parent.
8. Internal loopback requests cannot impersonate an ordinary user request.
9. No Agent execution route can reach the host-shell bridge.
10. Startup does not silently activate scheduled or autonomous work.
This is a proposed Odysseus test suite, not a claim that all ten tests already exist upstream.

8. Phase 2.1 conclusion
Audit findings established
We have confirmed that upstream provides a useful central authorization framework, but its standard security model is not the same as our intended Agent security model.

Three requirements must be addressed before implementation:
1. Independent Agent identity and capability policy — administrator status and disabled authentication must never grant ordinary-Agent privileges.
2. Complete execution-path closure — MCP, host-shell bridges, alternate routes and background execution must be disabled or separately controlled.
3. Explicit startup profile — no hidden scheduler, poller, auto-connect or autonomous execution.
The most important architectural decision is now clear: we should not try to make the ordinary Agent a less privileged administrator. We should give it a separate, narrowly defined execution identity.
