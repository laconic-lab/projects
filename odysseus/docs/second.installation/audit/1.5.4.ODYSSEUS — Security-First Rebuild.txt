# ODYSSEUS — PHASE 1.4

## Secure Installation & Runtime Foundation



Phase 1.3 — CLOSED

Phase 1.4 — NEXT



### 1. Mission

Build and install Odysseus as a local-first, security-controlled AI Agent and orchestration platform on the Steam Deck OLED.

The objective is not merely to get Odysseus running.

The objective is to establish a reliable, isolated and maintainable runtime in which Odysseus can coordinate local AI models and, when explicitly authorized, external cloud AI providers — without giving the conversational Agent unrestricted access to the Steam Deck host, personal files, credentials, network or execution environment.

Security must be part of the installation architecture, not something added afterwards.

### 2. Architectural objective

The intended architecture separates reasoning from authority:

- Conversational Agent: reasoning, planning, dialogue and orchestration.
- Policy enforcement: controls which capabilities can be requested, by whom and under what conditions.
- Read-only inspection: access to explicitly approved project information.
- Execution broker: controlled execution of approved operations, with authorization and resource limits.
- Provider broker: manages access to external AI providers without exposing credentials to the Agent.
- MCP gateway: controlled access to approved MCP servers and tools.
- Isolated runtime: prevents the application and its subprocesses from inheriting unrestricted Steam Deck host authority.

The architecture must support local models as the default reasoning option and external providers as optional, explicitly enabled capabilities.

### 3. Security requirements inherited from Phase 1.3

The source audit identified 22 findings, including several critical privilege-boundary concerns.

Phase 1.4 must address the underlying risks rather than merely hide tools or change interface settings.

In particular:

1. Prevent unrestricted Bash/Python execution from becoming host-level authority.
2. Enforce authorization at execution time, not only in model-facing tool schemas.
3. Restrict internal API access through explicit method and route allowlists.
4. Prevent MCP subprocesses from inheriting application secrets.
5. Enforce MCP tool restrictions at runtime.
6. Control background jobs, schedulers, pollers and automatic reconnection.
7. Restrict external integration API capabilities and prevent credential leakage in responses.
8. Isolate browser execution and eliminate uncontrolled package downloads.
9. Protect user data, provider credentials and configuration files.
10. Ensure that the Agent cannot bypass its policy through alternate execution paths.

The full audit register and its evidence remain in the exported Phase 1.3 conversation. The new chat must use that record as its security baseline.

### 4. Steam Deck deployment principles

The installation must respect the actual hardware and SteamOS environment.

- Dedicated Odysseus runtime boundary.
- Narrow, explicitly approved filesystem mounts.
- No broad host filesystem access.
- No host Podman socket exposure.
- No unrestricted host networking.
- Dedicated provider credentials outside the project and repository.
- No secrets committed to Git.
- Resource limits appropriate for a gaming-oriented device.
- No automatic startup.
- No persistent background activity unless explicitly approved.
- Manual start, stop, status, logs, backup and recovery procedures.

The existing Steam Deck configuration is historical reference only. Phase 1.4 must inspect the current environment before making assumptions or changes.

### 5. Installation methodology

Work must proceed in controlled, independently verified stages:

| Stage | Objective                                                                     |

| 1     | Inspect Steam Deck, Distrobox, Podman, storage and existing Odysseus remnants |

| 7     | Perform runtime and security acceptance tests                                 |

No stage should proceed on an unverified assumption.

### 6. Acceptance criteria

Phase 1.4 is not complete simply because the web interface opens or the Agent answers a question.

Completion requires evidence that:

- Odysseus starts and stops reliably.
- The intended local model works.
- External providers remain unavailable until explicitly configured and authorized.
- Credentials are not exposed to the Agent, MCP children or repository.
- Unapproved filesystem and execution operations are blocked.
- Background activity is disabled unless deliberately enabled.
- Runtime isolation and resource limits work as intended.
- LAN access is restricted to the intended devices.
- Backup and recovery procedures are tested.
- Security-relevant audit findings have been addressed or explicitly documented as accepted residual risks.

### 7. Rules of engagement

The new chat must follow these principles:

- Inspect first; modify second.
- Never delete or overwrite without inspection and confirmation.
- Never reuse historical configurations blindly.
- Never claim a security control works without testing it.
- Never silently downgrade security when a component fails.
- Never activate cloud providers or background services without authorization.
- Never compromise gaming performance through uncontrolled resource consumption.
- Preserve verified results and document every meaningful project change.

Odysseus should become a trustworthy local AI command centre:

A platform where local intelligence handles the default workload, cloud intelligence can be called when authorized, and specialized Agents can eventually perform increasingly complex tasks — all within clearly defined, independently enforced security boundaries.

The long-term vision is a capable AI orchestrator, not an unrestricted shell with a chatbot attached.
