## Phase 2.1 — Dispatch and authority audit

Read-only investigation

Our objective is to prove that an ordinary Odysseus Agent cannot bypass its restricted permissions, regardless of how a tool call is submitted.

I'll examine these execution paths in order:

1. Native tool dispatch — can a model call a blocked tool directly?
2. MCP dispatch — can a disabled or unknown MCP tool still execute?
3. Alternate execution routes — shell bridges, background jobs, browser automation and administrative routes.
4. Authority inheritance — can admin privileges or authentication-disabled mode accidentally grant ordinary-Agent permissions?
5. Regression coverage — which existing tests prove these boundaries, and which tests we must add.

The deliverable will be a dispatch security matrix:

| Execution path               | Required result               |
| ---------------------------- | ----------------------------- |
| Approved ordinary-Agent tool | Allowed within defined limits |
| Blocked native tool          | Rejected server-side          |
| Unknown tool                 | Rejected                      |
| MCP tool                     | Rejected                      |
| Directly forged tool call    | Rejected                      |
| Admin-only route             | Human administrator only      |
| Background execution         | Disabled                      |
| Provider selection           | Human-controlled              |

Important: We will not assume a security control works merely because its code exists. We need to identify its enforcement point and corresponding test.

No Deck commands, no installation, no API calls, no modifications.

Let's establish the dispatch boundary before touching anything.
