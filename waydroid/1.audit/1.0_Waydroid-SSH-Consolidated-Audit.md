## 1. Executive summary

### Project objective

Run Android on the Steam Deck OLED, with the Deck performing Android CPU
and GPU work, while Linux Mint and Windows act as remote display/input
clients. SSH is a mandatory control and secure transport mechanism.

### Mandatory architecture and constraints

-   Waydroid must run inside a container environment: rootless Podman
    and/or Distrobox.
-   **No native Waydroid installation on SteamOS.**
-   The former Ryan Rudolf native SteamOS installer is reference
    material only.
-   SSH access from Linux Mint and Windows is mandatory.
-   Prefer an individual Android window on the client, not the entire
    Deck desktop.
-   Reuse the existing KDE Wayland session; do not create another
    compositor without a demonstrated need.
-   No privileged container, broad host filesystem mounts, host
    network/PID/IPC sharing, or unnecessary device passthrough.
-   No host-wide firewall, forwarding, kernel, service, or package
    changes merely to force success.
-   Existing Pi-hole, Stable Diffusion, LocalAI/Shyrka, Odysseus and
    other projects are protected.
-   No autostart unless explicitly approved.
-   Diagnosis before modification; backup before any future edit;
    destructive actions require explicit approval.
-   A finding that secure container deployment is infeasible is an
    acceptable and successful audit outcome.

### Current verdict

**Conditionally promising, not yet proven.**

The strongest positive results are: - Rust BinderFS mounts inside
rootless Podman when `CAP_SYS_ADMIN` is granted to a disposable test
container. - The three Waydroid Binder device nodes can be created
inside that BinderFS instance. - The Binder device opens and responds to
`BINDER_VERSION`, protocol version 8. - Nested user namespaces can be
created inside rootless Podman when the tested capability set includes
`CAP_SETFCAP`. - Host-side private namespace networking supports bridge,
forwarding and NAT operations. - The existing KDE Wayland session,
socket, runtime directory and GPU render node are present.

The major unresolved obstacles are: - Podman container cgroup mount is
read-only and exposes no delegated child controllers. - Rootless Podman
container networking could not change its own `net.ipv4.ip_forward` with
only `CAP_NET_ADMIN`; bridge/NAT operations were not reached in that
test. - Actual nested LXC has not been run. - Binder transactions and
Android service stability have not been tested. - GPU use from the
proposed container, Wayland/D-Bus/audio handoff, ADB and end-to-end
scrcpy transport have not been tested. - The minimum capability set for
nested UID/GID mapping has not been fully reduced or retested under
Podman's default seccomp profile.

No Waydroid installation or persistent host modification is authorized
by this audit.

## 3. Project architecture

### Intended architecture

``` text
LINUX MINT CLIENT                         WINDOWS CLIENT
  SSH client                                SSH client
  scrcpy / ADB client                       scrcpy / ADB client
       |                                         |
       +------------- SSH tunnel ----------------+
                         |
                         v
STEAM DECK OLED — STEAMOS HOST
  SSH service
  KDE Plasma / KWin Wayland session
  AMD Van Gogh GPU / amdgpu
  Rootless Podman
       |
       v
  Dedicated Waydroid container environment
  (Distrobox may provide the userspace environment)
       |
       v
  Waydroid service manager
       |
       v
  Inner LXC Android container
       |              |              |
     Binder          GPU          Android data
     devices       render node     persistent store
       |
  Android applications
```

### Execution modes

Two launcher interfaces were proposed:

-   `waydroid_deck_start.sh` --- start the containerized Android runtime
    for local use on the Deck.
-   `waydroid_ssh_start.sh` --- start/control the same containerized
    runtime for remote use over SSH and prepare the remote display path.

These are two operating modes, not two separate Android installations.
Android state should not be duplicated accidentally.

### Remote display design

The documented candidate is scrcpy over an SSH tunnel. The intended
design keeps ADB and scrcpy transport off the unprotected LAN. ADB
should remain bound to localhost on the Deck, with client traffic
carried through SSH forwarding.

This design is documented in principle, but the complete Waydroid +
SteamOS + ADB + SSH + scrcpy chain has not been tested.

A separate Android window is the target. scrcpy mirrors and controls an
Android display; it does not by itself prove that each Android
application can be exported as an independent client-side window.
Waydroid multi-window mode and remote individual-window capture are
separate questions.

## 5. Historical chronology

1.  **Initial goal:** launch Android workload on the Deck while
    displaying and controlling it from Linux Mint through SSH.
2.  **Remote display options:** scrcpy, Sunshine/Moonlight and remote
    desktop were considered. scrcpy became the leading candidate because
    it supports a separate Android display window and documents SSH
    tunnelling.
3.  **SteamOS inspection:** confirmed SteamOS, kernel, AMD GPU, KDE
    Wayland session and a headless SSH shell.
4.  **Binder investigation:** identified Rust Binder, BinderFS
    registration and the absence of pre-created Binder nodes.
5.  **Waydroid source inspection:** reviewed Binder setup, LXC device
    mounts, session manager, ADB helper and network scripts.
6.  **Container scope corrected:** the former Ryan Rudolf installation
    was native to SteamOS and is historical reference only. The required
    target is container-only.
7.  **Podman baseline:** confirmed rootless Podman 6.0.2 and existing
    projects. Direct rootless Podman is used to isolate the runtime
    boundary before adding Distrobox.
8.  **BinderFS host tests:** mounted BinderFS and created the three
    Binder nodes inside disposable host user/mount namespaces.
9.  **BinderFS Podman tests:** mounting initially failed without
    capabilities; succeeded with only `CAP_SYS_ADMIN`; corrected ioctl
    then created all three Binder nodes and queried protocol version 8.
10. **Cgroup inspection:** host cgroup v2 and user-service delegation
    were observed; inside a strict rootless Podman container,
    `/sys/fs/cgroup` was read-only and `cgroup.subtree_control` was
    empty.
11. **Networking:** private host user/network namespace successfully
    created a bridge and performed namespace-local forwarding/NAT. A
    rootless Podman container with `NET_ADMIN` could not set
    `net.ipv4.ip_forward`; bridge/NAT were not reached in that attempt.
12. **Nested UID/GID mapping:** host nested user namespace succeeded.
    Inside Podman, strict capability sets failed. Default capabilities
    succeeded. Subsequent tests isolated `CAP_SETFCAP` as sufficient
    when combined with `SETUID`, `SETGID`, and `SETPCAP`.
13. **Current stopping point:** Test 20, removing `SETPCAP` from the
    successful combination, has been proposed but no result is recorded.

## 8. Rejected, failed and superseded approaches

1.  **Native Ryan Rudolf installation as the target:** rejected. It is
    reference material only.
2.  **Assuming Docker is the engine:** superseded. The host uses
    rootless Podman 6.0.2; Docker executable was not found.
3.  **Copying existing Distrobox security settings:** rejected. Existing
    boxes are privileged, share host namespaces and mount broad host
    paths.
4.  **BinderFS without `CAP_SYS_ADMIN` inside Podman:** failed in the
    strict disposable test.
5.  **Treating the first `EINVAL` ioctl as a Binder limitation:**
    invalidated. The request and structure were incorrectly encoded;
    corrected ioctl passed.
6.  **Rootless Podman `NET_ADMIN` as proof of full Waydroid
    networking:** not established. Forwarding sysctl failed before
    bridge/NAT were tested.
7.  **Assuming cgroup v2 visibility means nested LXC cgroup
    delegation:** rejected. Container cgroup mount was read-only and
    subtree delegation empty.
8.  **Assuming nested user namespaces are impossible in Podman:**
    superseded. They work with a specific capability set including
    `SETFCAP`.
9.  **Disabling seccomp alone or removing `no_new_privs` alone to fix
    UID mapping:** tested and insufficient.
10. **Installing packages on SteamOS for Binder testing:** avoided. The
    ioctl test was performed with existing Perl/Python tooling.
11. **Changing host IP forwarding or firewall to force Waydroid:** not
    approved.
12. **Using a separate compositor by default:** not selected; first
    attempt should reuse KDE session if technically possible.

## 9. Security considerations

### Outer container security

The existing Distroboxes are not acceptable templates for the target.
Their inspected configuration included: - `Privileged=true` - host
network, PID and IPC namespaces - `apparmor=unconfined` - SELinux label
disabled - broad read-write `/home/deck`, `/dev`, `/sys`, `/tmp` and `/`
mounts - no explicit capability drops

Rootless Podman does not make those broad mounts harmless. Container
root maps to host UID 1000, the Deck user.

### Binder

-   BinderFS mount succeeded with `CAP_SYS_ADMIN`.
-   `CAP_SYS_ADMIN` is broad; do not assume it is acceptable
    permanently.
-   Binder device nodes were mode `0600` and namespace-local root-owned.
-   Waydroid upstream was inspected as changing Binder permissions to
    `0666`; that broad access must be assessed, not copied
    automatically.

### Networking

Waydroid upstream network script was inspected as: - creating
`waydroid0` - enabling IPv4 forwarding - adding firewall/NAT rules -
starting dnsmasq - using a private Android subnet - removing its
bridge/rules on shutdown

The shutdown path was observed not to restore the previous
`net.ipv4.ip_forward` value. Any future design must preserve/restore the
prior state and avoid interference with Pi-hole.

### KDE session

An ordinary SSH shell does not inherit `WAYLAND_DISPLAY`, `DISPLAY` or
the desktop D-Bus session. The existing socket and runtime directory are
present, but the exact safe session handoff is untested. Do not copy the
entire host runtime directory into a container without a specific access
audit.

### Credentials and data

-   No credentials should be embedded in scripts, logs or container
    images.
-   Android userdata must be in a dedicated persistent directory, not a
    broad host directory.
-   Any future backup/recovery procedure must be tested before relying
    on it.
-   No destructive cleanup or reset without explicit approval.

## 10. Outstanding issues

### Critical feasibility gates

1.  **Test 20:** remove `CAP_SETPCAP` from the successful nested UID
    mapping combination.
2.  Test the resulting minimum set with Podman's default seccomp
    profile; do not assume seccomp can be relaxed permanently.
3.  Determine whether nested mount and PID namespaces work with the
    reduced capability set.
4.  Resolve cgroup delegation: can LXC run in a reduced/no-cgroup mode,
    or is writable delegated cgroup access essential?
5.  Test nested LXC itself in a disposable container, only after
    namespace/cgroup prerequisites are understood.
6.  Test Binder device access through the LXC device boundary.
7.  Test AMD render-node access using only the required device path and
    permissions.
8.  Test KDE Wayland, D-Bus and audio session integration without broad
    runtime mounts.
9.  Resolve Android networking inside the rootless Podman boundary. The
    `NET_ADMIN` forwarding failure remains; bridge/NAT in Podman are
    still untested.
10. Verify ADB authentication, localhost binding and SSH tunnel details
    for both Mint and Windows.
11. Assess Rust Binder stability under realistic Android workloads,
    including the reported large-transaction `ENOSPC` concern.

### Not yet justified

-   Creating a permanent Waydroid Distrobox.
-   Installing Waydroid.
-   Importing a native SteamOS installer.
-   Modifying SteamOS kernel parameters/modules.
-   Creating persistent BinderFS mounts/services.
-   Enabling host forwarding.
-   Granting privileged mode or broad host namespaces.

## 11. Recommended next steps

Proceed in this order:

1.  Execute Test 20, already defined in the historical source and below.
2.  If it passes, test the reduced capability set under Podman's default
    seccomp profile.
3.  Test nested mount and PID namespaces using the smallest successful
    set.
4.  Evaluate cgroup strategy against actual LXC requirements; do not
    repeat the source inspection.
5.  Run a minimal disposable LXC feasibility test only if the

6.  If LXC is viable, test Binder device handoff and GPU render-node

7.  Test Wayland/D-Bus/audio session handoff.
8.  Test Android network setup without changing host forwarding or
    Pi-hole.
