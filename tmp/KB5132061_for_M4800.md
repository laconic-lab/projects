## 18. TEST-39 — third-party DCM decoder source review (2026-11-11)

**Purpose:** Review the proposed Win-CBS-Manifest-Decoder implementation and documented pipeline without downloading, installing, cloning, or executing it.

**Sources reviewed (upstream `main`):**
- README: https://github.com/martinosani/Win-CBS-Manifest-Decoder/blob/main/README.md

### Findings

1. **The proposed approach matches the identified file format.** The decoder expects the four-byte `DCM\x01` wrapper, removes those four bytes, and applies the remaining PA30 delta to a base dictionary. The research describes the required base as resource type `0x266` (decimal 614), resource name `1`, embedded in `wcp.dll`. This is consistent with TEST-37's observed `DCM\x01PA30` header.

2. **The exact dictionary is a hard prerequisite.** The decoder does not derive or discover the dictionary itself. The separate PE-resource script must first extract the correct resource from a suitable `wcp.dll`. TEST-38 did not find `wcp.dll` in System32; no resource extraction can be approved until the actual candidate DLL and its resource identity are established. A dictionary from an unrelated Windows build must not be assumed compatible.

3. **Delta API choice:** the research reports that the Windows servicing implementation examined on build 26200 used `UpdateCompression.dll` and `ApplyDeltaB`; it also reports that `msdelta.dll` supports PA30/PA31. For this machine, the already-present, Microsoft-signed `UpdateCompression.dll` is the closer match to the described CBS path. This is research evidence, not proof that the supplied Python wrapper is correct for every DLL build. Microsoft documents the ApplyDeltaB buffer interface and requires the returned buffer to be freed with `DeltaFree`.

4. **Decoder implementation review:**
   - Uses 64-bit ctypes structures for `DELTA_INPUT` and `DELTA_OUTPUT`, passes the two input structures by value, and calls `DeltaFree` after copying successful output.
   - Pins Python input buffers for the duration of the native call.
   - Does not write to the input manifest or the dictionary. Single-file output is written only when an output path is supplied; batch mode creates a separate output directory.
   - It does not validate the dictionary's origin/build, verify the resulting XML, or independently verify the target manifest's identity. Those checks must be performed outside the decoder.
   - It loads the DLL using a bare name (`ctypes.WinDLL(args.dll)`). Do not use this default loading behavior in an approved run: use an explicitly verified absolute path under `%SystemRoot%\System32` to avoid ambiguity about which DLL is loaded.
   - On API failure it reports `ctypes.GetLastError()`, but the DLL is not loaded with `use_last_error=True`; therefore the reported error value may not reliably represent the native call's last-error value. Treat any such error number as provisional.
   - The resource extractor's `--id 614` matching logic accepts a matching ID at any level of the resource path and selects the last matching leaf. It does not explicitly require the full resource path type=614, name=1, language=the intended language. Its listing mode should be used first; no blind resource dump is approved.
   - The MSU/WIM extraction PowerShell scripts delete extracted CAB files by default after successful expansion, and `-Force` deletes an existing output directory. If those scripts are ever considered, use a new empty output location, preserve CABs with `-KeepCabs`, and do not use `-Force`. They are not needed for the immediate local-manifest decoding question.

5. **Security and scope:** The repository is GPL-3.0 according to its README. The reviewed scripts are third-party code and have not been executed or downloaded. Static source review does not establish that the code is bug-free or that the decoded result is trustworthy without independent validation.
