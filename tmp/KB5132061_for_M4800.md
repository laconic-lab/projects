#### 5.3.5 Assessment — is KB5132061 a wall, and is there a workaround?

**Confirmed for this machine:** the current Windows Update delivery attempt is blocked by a TPM 2.0 compatibility hard block. The attempt did not reach an ordinary CBS package-install failure; Setup stopped in its compatibility scan.

**Not established:** that the KB5132061 package itself universally requires TPM 2.0 when installed as a monthly cumulative update, that Microsoft intentionally changed the monthly LCU policy in November 2026, or that every subsequent cumulative update will be blocked in the same way. Microsoft's release notes do not list TPM 2.0 as a KB5132061 prerequisite. The observed block is in the Setup compatibility path used by this attempt.

**No verified workaround found:** no public workaround was found that specifically resolves KB5132061 / `0xC1900201` / `TpmVersion` on an unsupported M4800-class device.

**Potential route to evaluate, not yet validated:** Microsoft's official x64 Catalog instructions provide a direct MSU/DISM package-servicing route, with the KB5043080 checkpoint package before KB5132061. Because DISM package servicing is distinct from the Setup UX path that produced the TPM HardBlock, it is reasonable to investigate whether a correctly staged and applicable package can be serviced without re-entering that compatibility scan. This is a hypothesis, not a confirmed bypass. The existing 110 CSI payload corruptions, historical DISM ACL error `0x80070228`, previous WUSA “not applicable” result, and checkpoint package state all make an immediate install attempt unjustified.

**Decision:** do not change BIOS/TPM settings, edit compatibility registry values, replace Setup/Appraiser files, rerun Rufus scripts, or attempt a manual MSU/DISM install yet. First complete the read-only CBS/package ownership investigation and verify the KB5043080 checkpoint state. Then review a narrowly scoped, reversible package-install feasibility plan. The goal is to test the documented servicing route only after its prerequisites and component-store risks are understood—not to force Setup to ignore the hard block.

### 5.4 Interpretation of the CBS payload findings

The recorded `CSI Payload Corrupt` entries identify component payload integrity failures, not necessarily entire update packages that are “damaged.” The CBS session is explicitly a detect-only operation and recorded 110 payload corruptions with zero repairs. Current evidence does not identify why those payloads became corrupt.

Potential causes such as an interrupted servicing transaction, storage/filesystem faults, third-party modification/cleanup, or an earlier servicing defect remain hypotheses only. No causal evidence has yet been collected to select among them. The temporal proximity between the CBS scan and the KB5132061 failure does not establish that the payload findings caused `0xC1900201`.

The investigation must distinguish two independent diagnostic tracks:
1. **Setup compatibility track:** identify the exact source of `0xC1900201` in Windows Update / Setup logs and determine whether the operation performed a hardware eligibility check.
2. **Component-store integrity track:** resolve the 110 payload records, their owning components/packages, active-versus-staged state and source availability.

Neither track authorizes repair or installation by itself.
