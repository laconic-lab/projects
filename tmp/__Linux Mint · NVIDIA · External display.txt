One important clarification about updates
Your concern is valid, but there is a distinction worth keeping straight:
sudo apt update — refreshes the package lists. It does not install a new kernel or
compile an NVIDIA driver.
sudo apt upgrade — installs available package updates, potentially including a new
kernel. Kernel updates can trigger DKMS recompilation.
NVIDIA driver 580 — we should not assume that apt update will install it automatically.
What matters is which driver packages are actually installed or selected by an upgrade,
and whether DKMS successfully builds driver 470 for the running kernel.

470 version and DKMS status.
3. After a kernel update, verify that driver 470.256.02 built successfully for the new kernel
and that both displays still work.

This version uses your green, red and yellow messages properly. It also checks the actual

#!/bin/bash
# ---------- TERMINAL COLORS ----------
GREEN='\033[0;32m'
RED='\033[0;31m'
YELLOW='\033[1;33m'
RESET='\033[0m'
green() { printf "${GREEN}✔ %s${RESET}\n" "$*"; }
red() { printf "${RED}✘ %s${RESET}\n" "$*"; }
yellow() { printf "${YELLOW}⚠ %s${RESET}\n" "$*"; }
# ---------- NVIDIA / KERNEL CHECK ----------
nvidia_check() {
local stage="$1"
local running_kernel latest_kernel
local loaded_version module_version dkms_status
running_kernel=$(uname -r)
echo
echo "========== NVIDIA / KERNEL CHECK: $stage =========="
echo "Running kernel: $running_kernel"
# Check the currently loaded NVIDIA driver
if [[ ! -r /proc/driver/nvidia/version ]]; then
red "NVIDIA driver is not currently loaded."
return 1
fi
loaded_version=$(grep -m1 'NVIDIA UNIX' \
/proc/driver/nvidia/version |
grep -oE '[0-9]+\.[0-9]+\.[0-9]+' | head -n1)
if [[ "$loaded_version" != "470.256.02" ]]; then
red "Loaded NVIDIA version is ${loaded_version:-UNKNOWN}, not
470.256.02."
red "STOP: Review the NVIDIA driver state."
return 1
fi
green "Loaded NVIDIA driver 470.256.02 verified"
# Find the newest installed kernel
latest_kernel=$(find /lib/modules -mindepth 1 -maxdepth 1 \
-type d -printf '%f\n' | sort -V | tail -n1)
if [[ -z "$latest_kernel" ]]; then
red "No installed kernel module directories found."
return 1
fi
echo "Newest installed kernel: $latest_kernel"
if [[ "$latest_kernel" != "$running_kernel" ]]; then
yellow "Newest kernel differs from the running kernel."
yellow "A reboot may be needed after verifying the new kernel."
fi
# Check NVIDIA module available for the newest installed kernel
module_version=$(modinfo -k "$latest_kernel" \
-F version nvidia 2>/dev/null)
if [[ "$module_version" != "470.256.02" ]]; then
red "NVIDIA module for $latest_kernel is ${module_version:-NOT
FOUND}."
red "Expected 470.256.02. STOP MAINTENANCE."
return 1
fi
green "NVIDIA 470.256.02 module verified for $latest_kernel"
# Verify DKMS registration for that specific kernel
dkms_status=$(dkms status 2>&1)
echo
echo "DKMS status:"
printf '%s\n' "$dkms_status"
if ! grep -F "nvidia/470.256.02, $latest_kernel," \
<<< "$dkms_status" | grep -q 'installed'; then
red "DKMS does not confirm NVIDIA 470.256.02 installed for
$latest_kernel."
red "STOP MAINTENANCE and review DKMS."
return 1
fi
green "DKMS registration verified for $latest_kernel"
}
# ---------- SYSTEM MAINTENANCE ----------
nvidia_check "BEFORE UPDATE" &&
sudo apt-get update &&
sudo apt-get upgrade &&
nvidia_check "AFTER APT UPGRADE" &&
flatpak update &&
{
echo
echo "========== APT AUTOREMOVE PREVIEW =========="
preview=$(sudo apt-get autoremove --dry-run 2>&1) || {
echo "$preview"
exit 1
}

Getting burned once by a graphics-driver update is annoying. Getting burned a second time
and losing your external monitor configuration while trying to recover a 2014-era workstation
is another level of frustration.
And your M4800 isn't just a laptop with an old GPU. It's a working machine with a very specific,
proven configuration.
Why the second incident was worse
Your Quadro K2100M uses NVIDIA's Kepler architecture. The proprietary legacy driver branch
is the important constraint here.
There are three separate things that can go wrong:
Kernel update: Linux installs a new kernel, and DKMS must build the NVIDIA module for
it.
Driver mismatch: the module for the new kernel is missing, fails to compile, or belongs to
an incompatible driver version.
Display configuration: Xorg or PRIME configuration changes can affect which GPU drives
the internal panel and the external monitor.
Your first repair commands adjusted Xorg configuration, selected NVIDIA PRIME and
regenerated initramfs. Those changes may have helped restore the display at the time, but
they aren't a universal repair procedure for every NVIDIA failure.
The second incident is precisely why we shouldn't automatically repeat those commands.
What I like about secureupdate
Your new workflow adds a preventive check instead of waiting until you're staring at the 14-
inch internal panel wondering where your 28-inch monitor went.
You said:
One caveat worth keeping in mind: the current script checks the NVIDIA module version and
DKMS status, but it cannot guarantee that every future kernel will work with driver 470. A
module can exist and still fail to load or work correctly.
For that reason, I'd keep these rules:
1. Check the known-good NVIDIA 470.256.02 state before updating.
2. Stop if the expected module is missing or a different version is detected.
3. After an update, verify the driver and external display.
4. Never run the old repair commands blindly; diagnose first.
And one small correction to our earlier discussion: apt-get upgrade doesn't normally
recompile the Linux kernel itself. It can install a new kernel package, after which DKMS
attempts to compile the NVIDIA module for that kernel. That distinction helps us identify
exactly what failed.
The goal isn't to stop updating your M4800. It's to stop an ordinary maintenance session
from becoming another graphics recovery operation.
Your veteran workstation deserves a maintenance routine with a little more respect. 😄
