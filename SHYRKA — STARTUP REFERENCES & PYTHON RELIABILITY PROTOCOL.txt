## 4. Mandatory Python and Shell Reliability Rules

Before generating or running commands:

1. **Establish the target environment.** Identify SteamOS host, `localai-box`, or another explicitly named container.

2. **Inspect before assuming.** Verify the actual project directory, relevant files, filenames, and existing project structure before proposing changes.

3. **Verify executables and versions.** Check the available Python interpreter, package manager, test runner, and other tools relevant to the task.

4. **Prefer the existing virtual environment.** Use `./.venv/bin/python` for project commands unless inspection establishes a justified alternative.

5. **Use the supported test runner.** `unittest` has previously been verified. Check current project evidence before choosing a different runner.

6. **Never invent facts.** Do not fabricate package availability, APIs, filenames, paths, command output, configuration values, test results, or successful operations.

7. **Keep commands explicit and minimal.** Commands must fit the verified environment and perform only the required operation.

8. **Inspect before modifying.** Read the relevant files, understand their current state, and make a backup before writing changes.

9. **Make the smallest justified change.** Avoid broad rewrites, unrelated refactoring, destructive operations, and unnecessary dependency changes.

10. **Use guarded file operations.** Where appropriate, use assertions, precondition checks, and atomic file replacement. Verify the final contents after writing.

11. **Diagnose actual failures.** If a command fails, inspect the error and relevant environment before proposing a correction. Do not repeatedly guess at fixes.

12. **Respect authorization boundaries.** Do not install dependencies, alter configuration, restart services, introduce automatic startup behavior, or modify unrelated projects unless explicitly required and authorized.

13. **Verify the result.** Read back modified files and run appropriate checks. Report only checks actually performed and their observed results.

14. **Distinguish verification levels.** A successful syntax check does not prove application correctness. A passing unit test suite does not prove every feature works. State what was and was not verified.

15. **Preserve working state.** If the environment or project state differs from expectations, stop and investigate before proceeding with a potentially disruptive change.

## 5. Mandatory Current-Chat Project Scope

### 5.1 Scope lock

The project and task established by the current conversation define the scope of work.

1. Identify the active project, canonical path, current task, and last verified state from the conversation, handover, and authoritative references.
2. Treat the identified project as the sole default search boundary.
3. Do not scan every project, Distrobox, recovery directory, or the entire Steam Deck filesystem.
4. Do not restart discovery from zero after a pause or handover when existing evidence is sufficient.
5. If the active project or its path cannot be established confidently, inspect only the relevant evidence and ask for clarification before modifying files.

### 5.2 Shared startup references

Use the authoritative GitHub references as the initial project map:

- Master history: https://github.com/laconic-lab/tmp/blob/main/PROJECT_VERSIONS.txt
- Shyrka manifest: https://github.com/laconic-lab/tmp/blob/main/SHYRKA-AGENT-MANIFEST.txt
- Shyrka release notes: https://github.com/laconic-lab/tmp/blob/main/SHYRKA_RELEASE_NOTES.txt
- Startup and Python reliability protocol: https://github.com/laconic-lab/tmp/blob/main/SHYRKA%20%E2%80%94%20STARTUP%20REFERENCES%20%26%20PYTHON%20RELIABILITY%20PROTOCOL.txt

Consult references already available in the conversation without unnecessarily retrieving them again. Check current remote contents when relevant and accessible.

These references provide context; they do not prove that the current local working tree or runtime matches the documented state.

### 5.3 Targeted local discovery

Within the active project's scope:

1. Inspect the known project root, relevant files, and established documentation paths.
2. Select only the documentation justified by the current change.
3. Include the master project history only when the change warrants an entry under its established conventions.
4. Update the project manifest when its inventory or documented configuration changes.
5. Update project release notes when a meaningful change merits a release-history entry.
6. Do not update every document automatically when a single authoritative record is sufficient.
7. Exclude historical backups, patch backups, and archived copies from active editing unless recovery or historical comparison is the explicit task.
8. Do not expand discovery into unrelated projects merely because a shared document mentions them.

### 5.4 Documentation accuracy and safe updates

Before writing:

1. Read the selected local files and identify the exact insertion points.
2. Distinguish historical information, planned work, and currently verified facts.
3. Create verified pre-update copies of every document to be changed.
4. Make the smallest justified changes, preserving existing history and conventions.
5. Do not modify application code, configuration, dependencies, databases, services, or unrelated files during a documentation-only task.

After writing:

1. Read back every modified document.
2. Verify expected entries, preserved history, and absence of unintended duplicates.
3. Verify backups exist and are readable.
4. Check hashes and file sizes or line counts where practical.
5. If verification fails, stop, report the failure, and restore only when the verified backup and restoration procedure are unambiguous. Verify restoration afterward.
6. Do not claim GitHub and local files are synchronized unless both states have actually been checked.

### 5.5 Resume checkpoint

After a long pause or when continuing in another chat, establish:

- Active project and canonical path.
- Current task and last verified state.
- Files already changed and backup locations.
- Checks actually performed and their observed results.
- Outstanding issue and the single justified next action.
- Existing safety restrictions and exclusions.

Verify only what is necessary to confirm that the recorded state remains valid. If the evidence conflicts, investigate that discrepancy before proceeding.

### 5.6 Completion report

Report the project and path, documentation updated, verified changes, backup location, read-back results, unresolved issues, and any skipped checks.

Explicitly confirm that unrelated projects and application files were left untouched.

**Operating rule:** Start from shared references, narrow discovery to the current project's actual needs, inspect before modifying, back up first, verify afterward, and stop when the requested task is complete.---

## 6. Shyrka Operating Guardrails

These constraints apply unless the user explicitly authorizes a specific change within the intended scope.

- **Local-first:** No cloud AI or external AI services unless explicitly authorized.
- **Manual start:** No new automatic startup behavior.
- **Read-only by default:** Use only explicitly approved tools and permissions.
- **No arbitrary shell execution by the agent.**
- **No mail-reading feature.**
- **Diagnose before modifying.**
- **Work incrementally:** Make one justified change at a time and verify it before continuing.
- **Protect unrelated projects and data.**
- **No unnecessary service restarts or configuration changes.**
- **No claims of success without evidence.**
- **No expansion of scope without authorization.**

Reading documentation does not grant permission to execute commands, modify files, access external services, or change the agent's permissions.

If a requested task conflicts with these guardrails, identify the conflict and obtain the required authorization before proceeding.

## 7. Start-of-Session Checklist

Before acting, establish:

- [ ] Which project and task are being continued?
- [ ] What is the canonical project path?
- [ ] Which execution environment is active?
- [ ] What was the last verified state?
- [ ] Which files, components, or services are actually in scope?
- [ ] Which Python executable and test runner are available, if relevant?
- [ ] Are the relevant local and remote references consistent?
- [ ] Is a backup necessary before the proposed modification?
- [ ] What is the single justified next step?

If a critical answer is uncertain, inspect only the relevant project evidence before proceeding.

Do not turn uncertainty into an assumption.

## 8. Session Handover and Resumption

When ending a substantial session or preparing to continue in another conversation, record:

1. **Task:** What was being worked on?
2. **Environment:** Where were commands executed?
3. **Last verified state:** What was actually inspected or tested?
4. **Files changed:** Which files were modified, if any?
5. **Backup status:** What was backed up and where?
6. **Checks performed:** Exact commands and observed outcomes where useful.
7. **Outstanding issues:** What remains unresolved?
8. **Next action:** One specific, justified action.
9. **Constraints:** Any permissions, exclusions, or safety requirements that remain in force.

Clearly distinguish completed work from proposed work.

A handover is a record of evidence, not proof that the current environment has remained unchanged.

On resumption, verify only what is necessary to establish that the recorded state is still valid.
